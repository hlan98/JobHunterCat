# DECISIONS — 关键设计决策

> ADR 风格记录。每条包含：**背景 / 决策 / 理由 / 代价**。
> 目的是让后来者知道"为什么是这样"，避免重复踩坑或无意推翻。

---

## ADR-1 用 Electron + Python 双进程，以 stdio JSON 通信

**背景**：业务逻辑（浏览器自动化 / LLM / 评分）在 Python 生态里最顺手；
界面（透明窗、动画帧、多窗口）只有 Electron 做得自然。

**决策**：两个独立进程。Python 只管业务逻辑，Electron 只管界面。
Python 每行 `print` 一个 JSON 事件给 stdout；Electron 主进程按行解析后转发给各窗口。
反向：Electron 每行写一个 JSON 命令到 Python 的 stdin。

**理由**：两边各用最合适的栈，不必互相迁就；stdio 是最简单的跨进程管道，不引入 IPC 依赖。

**代价**：进程生命周期、路径解析要自己管；事件契约必须两端成对维护（见 ARCHITECTURE 第四节）。

## ADR-2 接管用户已登录的浏览器，不接管账号密码

**背景**：自动化操作招聘平台，最省事的做法是程序自己登录。

**决策**：**不做**。程序通过 DrissionPage 接管本地 9222 调试端口上**用户已经手动登录好**的浏览器。
执行前检查端口是否监听；未监听直接报错，不自动新开浏览器。

**理由**：
- 不碰账号密码，避免凭证泄露风险
- 登录态由用户自己掌握，随时可终止
- 避免实现"自动登录"带来的验证码 / 风控对抗

**代价**：首次使用需用户自己登录；登录态过期需手动扫码（程序会检测并提醒）。

## ADR-3 保留 rehearsal（演练）模式

**决策**：保留 `rehearsal` 模式 —— 走完整流程但**不真实发送**。

**理由**：真实投递不可逆（打招呼、发简历发出去收不回来）。
给用户一个零风险验证筛选条件与流程的方式。

**代价**：两套路径要同时维护；演练结果的日志需明确标注"未真实发送"。

## ADR-4 只发在线附件简历，不兜底上传本地 PDF

**背景**：曾经的实现会在找不到在线简历时，兜底上传本地 PDF 文件。

**决策**：**删掉兜底**。只从用户在 BOSS 上**已上传**的附件简历里选一份发送。

**理由**：
- 用户明确要求：只发一开始选好的那一份
- 兜底上传可能发出**非预期**的简历文件（后果严重且不可逆）
- 没选完就停止，比悄悄用别的顶替更可控

**代价**：用户必须先在线上传简历；没选完会拦住不投。

## ADR-5 取元素文字**不能**用 `find_first`

**背景**：BOSS 的「请求简历卡片」是「标题 + 说明 + 按钮」的多段结构。

**决策**：读取消息文字时，**必须**在取第一个匹配节点后，
再用**整条消息的可见文字**兜底（更长者为准）。禁止只用 `find_first` 的结果。

**理由**（事故复盘）：原实现只取第一个匹配节点 → 只拿到卡片标题「看下简历」，
含「是否同意」的正文**整段丢失** → 卡片永远识别不出来 → 简历从未自动发出。
日志里「是否同意」出现 **0 次**，与症状完全吻合。

**代价**：取到的文字可能包含按钮文案，下游判定需容忍。

## ADR-6 卡片元素不要求 `item-friend` 类

**背景**：原实现要求消息元素带 `item-friend` 类才处理。

**决策**：放宽 —— 非 `item-friend` 的元素，**只要正文像请求简历卡片**
（含「是否同意」+ 简历/附件）就照样处理。

**理由**：BOSS 的系统卡片可能不带 `item-friend`。
严格过滤会让卡片连读都读不到，整条发送链路都不会启动。

**代价**：放宽可能引入噪声 —— 用**文本特征**收住（不是无脑放行所有消息）。

## ADR-7 推送式状态必须支持「窗口打开时回放」

**背景**：`progress` 事件只在投递过程中推送。

**决策**：`main.js` 缓存最近一次 `progress`（`lastProgress`），
看板窗口 `did-finish-load` 时**补发一次**。

**理由**：用户**中途打开看板**时，如果只靠推送，打开那一刻没有任何数据，
要等下一次事件（收集阶段 1~3 分钟一次）；若已接近尾声就再也等不到
→ 表现为"进度条不动"。

**代价**：需维护一份缓存状态；新增推送式事件时都要考虑回放。

> **通用教训**：**推送式状态 + 可随时开关的窗口 = 打开时是空的。**
> 凡窗口可随时开关的 UI，状态要么持久化、要么打开时补拉/回放。

## ADR-8 城市不在支持列表时**明确报错**，不静默回退

**背景**：原实现 `CITY_CODES.get(name, CITY_CODES["广州"])` ——
表外城市会**静默搜索广州**。

**决策**：表外城市 → 记日志 + 提示用户 + **中止**，不偷偷换城市。
同时把码表从 11 个扩充到 **63 个**。

**理由**：用户填「长沙」，程序一声不吭地搜广州 ——
用户以为在投长沙，实际在投广州。这是**程序悄悄做了用户没要求的事**。

**代价**：遇到未收录城市会停下来，需要扩充码表。

## ADR-9 关键词只增不减的护栏

**背景**：LLM 在两种场景会改动关键词：① 方案修订 ② 停止总结。

**决策**：两处都加护栏 —— **新增允许，删除必须用户在场且明确同意**。
不符合条件时不改，并在日志里写明。

**理由**：实测出现过用户没有要求、关键词却被删掉的情况。
关键词是用户的投放意图，丢失不可逆。

**代价**：方案灵活性略降。

## ADR-10 等待提示不进对话正文

**背景**：「正在分析…」「稍等…」这类等待提示如果被 LLM 当成用户的话，
会污染对话历史。

**决策**：`isTransient()` 判定为"等待提示"的文案 → 走**状态行**，
**不进**对话正文；而「请选择附件简历」这类**需要用户行动**的提示**必须留在正文**。

**理由**：历史污染会让 LLM 基于错误的上下文做判断。

**代价**：正则判定有误判风险 —— 已用 10 个样本做验证（3 条留正文 / 7 条走状态行）。

## ADR-11 合规措辞清理

**决策**：清理「模拟真人」「绕过X」「防风控」等表述，改为中性描述
（`请求节奏` / `避免频繁刷新`）。**保留**「风控」作为平台侧现象的客观描述。

**理由**：被清理的表述会被理解为"本工具在规避平台管控"；
而「风控」作为**风险信号触发停手**的描述属于安全设计，应保留。

**代价**：部分菜单文案变化（如「风控节奏」作为用户可见菜单名**保留未改**）。

## ADR-12 分文件许可 + 保守归类

> **术语更正（2026-09-24）**：本决策早先被称作「双许可（dual-licensed）」，**这个说法不准确** ——
> 「双许可」通常指「使用者可在两个许可之间任选其一」，而本项目的实际安排是
> **按文件边界适用不同许可**，使用者**没有选择权**。
> `README.md` 与 `NOTICE` 已同步更正。

**决策**：MIT 衍生部分保持 MIT；原创部分用 PolyForm Noncommercial 1.0.0。
**混合文件整体按 MIT** 处理。

**理由**：MIT 不允许对其代码追加限制。保守归类避免"把 MIT 代码宣称为自有"的风险。
实测混合文件中 87.8% 的行与基线一致（详见 [`CODE_PROVENANCE.md`](CODE_PROVENANCE.md)）。

**代价**：原创部分的商用限制**不能**覆盖 MIT 部分 ——
仓库整体不能一概宣称"禁止商用"。
