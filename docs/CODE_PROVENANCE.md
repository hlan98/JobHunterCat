## 一、为什么需要这份文件

本项目起源于一个第三方 **MIT** 项目（`job-hunter-skill`），在其基础上做了修改，
并新增了桌宠前端等原创部分。

MIT 许可对相关代码授予了广泛的使用、修改和分发权利，并要求保留
原版权声明与许可声明。

因此，本项目后续新增代码所采用的限制性许可证，不应被表述为
对原 MIT 代码本身增加限制，也不应否定原 MIT 授权已经授予的权利。

> **表述提示**：不要把 MIT 的义务概括为"保留声明 + 不得追加限制"这样的两条清单。
> 更准确的表述是：**本项目不能通过自身后续许可证条款，否定或限制原 MIT 授权已经授予的权利。**

同时，本仓库中存在**混合文件** —— 同一个文件里既有 MIT 代码，也有后续新增代码。
必须把边界说清楚，让任何人能自行核对。

## 二、三类文件

| 类别 | 含义 | 本仓库对应 |
|---|---|---|
| **① 纯原创** | 完全由 JobHunter Cat 新增，不含任何原项目代码 | `agent/main.py`、`agent/pet_bridge.py`、`desktop/`、`memory/`、`assets/`、文档 |
| **② 来源于原项目** | 来自原项目，当前版本未发现后续修改 | `examples/` |
| **③ ★ 混合文件** | **原本是 MIT 代码，之后被修改/增删 —— 同一文件里既有 MIT 代码，也有后续新增代码** | `boss/`、`agent/shared.py`、`agent/ledger.py`、`agent/doctor.py`、`agent/skill_entry.py`、`tests/` |

### ★ 混合文件为什么是重点

以 `boss_apply.py` 为例：

```
boss_apply.py
│
├── 来自原项目的代码            ← 占绝大多数（相对基线 92% 未变）
│
└── 后续修改 / 新增的代码        ← 少数（相对基线新增 76 行、删除 34 行）
```

**不能**因为"我改了一部分"就把整个文件按新许可授权 ——
该文件仍**整体包含 MIT 代码**，而 MIT 要求这部分继续适用 MIT。

## 五、测量方法与局限

### 方法

1. 取**最早可得的快照**：`找工作喵-完整版-2026-09-12-v7-fixed.zip`
   （经核对，2026-09-12 / 09-13 / 09-15 三个包中这些模块的字节大小完全一致，
   可认为代表同一基线状态）
2. 对每个模块，用 `difflib.SequenceMatcher` 做**逐行匹配**
3. 「未变行」= 匹配块总行数；「新增行」= 现有行数 − 未变行；「删除行」= 基线行数 − 未变行

### ⚠️ 局限（必须知道）

| 局限 | 说明 |
|---|---|
| **基线 ≠ 上游原始版本** | 2026-09-12 快照**本身已经是修改过的版本**。上游原始 MIT 版本与它的差异**无法从现有产物测出** |
| 因此 87.8% 的含义是 | "与 2026-09-12 基线一致"，**不等于**"与上游 MIT 原版一致" |
| 逐行匹配是近似 | 大段移动的代码可能被计为"新增+删除" |

### 这对结论有影响吗？

**不影响处置方向，但影响表述的精确度。**

- 无论如何，这些文件都**包含 MIT 代码** → 整体按 MIT 处理是正确且安全的
- 若你希望把"与上游原始版本的一致性"也量化，需要**获取上游原始仓库**再跑一次同样分析

## 七、维护规则

1. 新增文件默认归 **① 纯原创**
2. **不要**把混合文件改判为纯原创，除非能证明其不含原项目代码
3. 每次改动混合文件后，**重跑第三节的差异分析**并更新数字
4. 引入新的第三方代码时，在此登记来源与许可
5. 许可边界变动时，同步更新 [`../NOTICE`](../NOTICE) 与 [`../README.md`](../README.md)
6. **每次重大代码来源变化后重新审计，并更新"文件状态"中的日期**

### 如何重跑差异分析

第三节的数字由 [`scripts/provenance_diff.py`](../scripts/provenance_diff.py) 生成：

```bash
# 普通表格
python scripts/provenance_diff.py --baseline <基线包.zip>

# 直接输出可粘贴进本文档的 Markdown 表格
python scripts/provenance_diff.py --baseline <基线包.zip> --markdown
```

基线包为 2026-09-12 的完整包（见第五节）。
若基线包已不可得，需重新选择一个早期快照，并在第五节说明其来源与局限。

> ⚠️ 重跑后请**同时更新**：
> ① 第三节表格数字 ② 顶部「文件状态」中的日期 ③ 若分类有变，同步 NOTICE 与 README
